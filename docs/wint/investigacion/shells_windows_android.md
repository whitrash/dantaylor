# Opciones para construir WINT en Windows y Android: modelos de aplicación nativos y alternativas

## Resumen

- Fecha de corte de esta investigación: 7 de octubre de 2026. Las cifras de versión salen de registros primarios (NuGet, PyPI, npm, crates.io, Maven Central, proxy de Go, pub.dev) y de documentación oficial leída desde sus fuentes en GitHub, porque muchos sitios oficiales estaban bloqueados (ver el último apartado).
- Microsoft (documento del 13/02/2026) recomienda WinUI para proyectos nuevos, mantiene WPF, Windows Forms y Win32, y marca UWP como "solo seguridad y errores". .NET 10 es LTS hasta el 14/11/2028.
- WinUI 3 / Windows App SDK sigue sin API oficial de ícono de bandeja (propuesta WindowsAppSDK#713 abierta, "Future (backlog)"); Windows Forms trae NotifyIcon integrado y existe H.NotifyIcon (MIT) para WinUI, WPF, Uno y MAUI.
- Un servicio de Windows no puede mostrar interfaz ni ícono de bandeja (desde Windows Vista): el ícono debe vivir en un proceso de la sesión del usuario que hable con el núcleo por IPC o HTTP local; el arranque se resuelve con el Programador de tareas (disparadores al iniciar sesión, al arrancar el equipo, por hora).
- Con una sola base de código para Windows y Android existen hoy: .NET MAUI 10 (soporte hasta 11/05/2027, mucho antes que .NET 10 LTS), Avalonia 12 (MIT, TrayIcon nativo), Flutter 3.47.6, Compose Multiplatform 1.12.1 (Tray nativo), Tauri 2.12 (requiere Rust) y Wails v3 (beta). Electron cubre solo Windows y Capacitor solo Android/web.
- En Python no hay todavía una opción madura de una sola base de UI para ambas plataformas: Flet 1.0 salió el 14/09/2026 (tres semanas), BeeWare (Briefcase 0.4.5, Toga 0.5.7) es pre-1.0 y no implementa íconos de estado en Android, Kivy 2.3.1 es de diciembre de 2024, y PySide6 en Android figura como vista previa técnica en su documentación. pystray tiene su última versión en septiembre de 2023.
- Una PWA es la base común más barata: se instala en Edge/Chrome (Windows) y como WebAPK en Chrome con GMS (Android), pero exige HTTPS, no tiene ícono de bandeja y su sincronización periódica es experimental, solo Chromium y condicionada por la interacción del usuario. Además, por CORS no puede leer páginas de comercios: el scraping tiene que seguir en el núcleo Python.
- Android impone: WorkManager con mínimo de 15 minutos para trabajo periódico, restricciones para iniciar servicios en primer plano desde segundo plano, y desde el 30/09/2026 la verificación de desarrolladores (Brasil, Indonesia, Singapur y Tailandia primero; global en 2027), con cuentas de "distribución limitada" para aficionados (hasta 20 dispositivos, sin documento ni tarifa).
- Distribución en Windows: la cuenta de desarrollador individual de Microsoft Store es gratuita y la Store vuelve a firmar los paquetes MSIX; Azure Artifact Signing para individuos solo está disponible en EE. UU. y Canadá, o sea que una persona en Argentina no califica.
- Mantenimiento a 5 años: .NET 10 LTS (hasta 2028) y Python/web son los más estables; Windows App SDK se sirve ~1 año por versión mayor, Electron soporta solo las 3 últimas mayores (cadencia de 8 semanas), React Native soporta la última más dos menores, y Tauri 3 ya está en alfa (3.0.0-alpha.4, 01/10/2026).
- Recomendación en una línea: núcleo Python sin interfaz con API local + panel web instalable (PWA) como base común, un lanzador de bandeja mínimo en Windows, alertas por ntfy o Web Push en Android, y recién después un cliente nativo (Avalonia 12 o .NET 10 con WebView2) si la PWA se queda corta.
- Contradicciones registradas: el README de Tauri dice "Windows 7 y superior" pero el anuncio de 2.12 (26/09/2026) quita el soporte oficial de Windows 7; la página de canales de Windows App SDK (21/05/2026) lista 2.1.3 como última estable mientras NuGet publica 2.5.1 (16/09/2026); una búsqueda web afirmó que Toga no soporta íconos de estado en Windows, pero el código fuente de Toga 0.5.7 los implementa con WinForms.NotifyIcon.

### H4 — Ícono de bandeja: WinForms sí, WinUI 3 no (hay que usar un paquete de terceros)
- Afirmación: WinUI 3 / Windows App SDK no tiene API oficial de ícono de bandeja: la propuesta "Modern System Tray Icon" (microsoft/WindowsAppSDK#713, abierta el 08/04/2021) sigue abierta con hito "Future (backlog)" y sin declaración de plazos de Microsoft; la propuesta anterior en microsoft-ui-xaml (#2020) figura como "no propiedad del equipo de WinUI". Alternativas: Windows Forms NotifyIcon (integrado), la API Win32 Shell_NotifyIcon (documentación de 2018) y la biblioteca H.NotifyIcon (MIT; WPF, WinUI, Uno.Skia.WPF, MAUI y consola; última versión estable 2.4.1 del 01/12/2025). Salvedades técnicas: H.NotifyIcon identifica cada ícono con un GUID que Windows asocia a la ruta del ejecutable salvo que esté firmado con Authenticode (el mismo criterio documenta Electron para su parámetro guid); y la guía Win32 indica que, en Windows 7, un ícono nuevo va al área de desbordamiento y "solo el usuario puede promoverlo" a la zona visible, de modo que el ícono de WINT puede quedar oculto por defecto (comportamiento en Windows 11 no verificado). Las notas de Windows App SDK hasta 2.1.3 no mencionan ninguna API de bandeja; que 2.2 a 2.5 la hayan agregado no está verificado.

### H6 — PWA instalable en Windows (Edge/Chrome): qué da y qué no
- Afirmación: Según la documentación de Edge (ms.date 10/15/2025), una PWA instalada se ancla a la barra de tareas y al menú Inicio, y puede configurarse para iniciar automáticamente al iniciar sesión en Windows; la documentación no menciona ícono de bandeja. Una PWA no necesita service worker para poder instalarse, pero sí un manifiesto y servirse por HTTPS (o localhost/127.0.0.1; es un requisito más estricto que "contexto seguro"). Trabajo en segundo plano: Background Sync, Periodic Background Sync y Background Fetch; la sincronización periódica solo ocurre en una red conocida, `minInterval` es solo un mínimo (el navegador pondera la conexión y cuánto interactúa el usuario con la app) y requiere permiso. MDN marca la API como experimental y aclara que en Chrome el permiso se concede solo a una app web instalada y lanzada como aplicación aparte; Chrome usa además la puntuación de interacción del sitio. Las notificaciones push las envía el servidor aunque el usuario no esté usando la app (se requiere permiso y suscripción). Conclusión técnica: una PWA sirve como panel y recibe avisos, pero no es un planificador confiable ni tiene bandeja; esas dos funciones quedan para el núcleo y un lanzador nativo.
- Fuentes: https://raw.githubusercontent.com/MicrosoftDocs/edge-developer/main/microsoft-edge/progressive-web-apps/ux.md, https://raw.githubusercontent.com/MicrosoftDocs/edge-developer/main/microsoft-edge/progressive-web-apps/how-to/background-syncs.md, https://raw.githubusercontent.com/MicrosoftDocs/edge-developer/main/microsoft-edge/progressive-web-apps/how-to/push.md, https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/api/web_periodic_background_synchronization_api/index.md, https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/progressive_web_apps/guides/making_pwas_installable/index.md, https://learn.microsoft.com/microsoft-edge/progressive-web-apps/how-to/background-syncs

### H7 — PWA en Android, empaquetado TWA y la barrera de CORS
- Afirmación: MDN indica que en Android solo Chrome (en dispositivos con Google Mobile Services) y Samsung Internet (en Samsung) instalan una PWA como WebAPK; Firefox, Edge, Opera y Chrome sin GMS solo crean un acceso directo con insignia del navegador. La instalación exige HTTPS (o localhost/127.0.0.1), de modo que una página servida por HTTP en la red local no se instala. Bubblewrap CLI (Google Chrome Labs, Apache-2.0, versión 1.25.0 del 31/07/2026, requiere Node 18 o superior) genera proyectos de Android que lanzan una PWA con Trusted Web Activity, vía para tener un APK propio sin escribir código nativo. Por la política de mismo origen y CORS, un script en el navegador solo puede pedir recursos del mismo origen salvo que la respuesta traiga cabeceras CORS: una PWA no puede leer el HTML de otros comercios; el rastreo de precios debe ejecutarse en el núcleo (Python) y la PWA solo consume su API.

### H8 — Android: límites de ejecución en segundo plano
- Afirmación: En la documentación de Android, el intervalo mínimo de trabajo periódico con WorkManager es de 15 minutos ("igual que la API JobScheduler"); WorkManager guarda el trabajo en SQLite interno, sobrevive a reinicios y respeta el modo Doze. Las apps que apuntan a Android 12 (API 31) o superior no pueden iniciar servicios en primer plano desde segundo plano (lanza ForegroundServiceStartNotAllowedException) salvo excepciones: mensajes FCM de alta prioridad, eventos de arranque (ACTION_BOOT_COMPLETED), alarmas exactas por acción pedida por el usuario, o que el usuario haya desactivado la optimización de batería para la app. Implicancia para WINT: vigilar precios cada pocos minutos desde el teléfono no es viable de forma confiable; conviene que el núcleo (en la PC o en un servidor) detecte la oferta y empuje el aviso (FCM, ntfy o Web Push), dejando en el teléfono solo la recepción y la visualización.
- Fuentes: https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work, https://developer.android.com/develop/background-work/background-tasks/persistent, https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start
- Confianza: alta
- Riesgo: alto
- Vigencia: consultado 7 de octubre de 2026

## Recomendaciones para WINT

1. Definir WINT como un "concentrador de módulos" y no como una app monolítica: cada programa casero (Detector, catálogos, Osi, Sol, Luna) expone un contrato mínimo (manifiesto JSON con nombre, comando, horarios y salidas, más una API HTTP local con OpenAPI). Por qué: la idea de "plataforma Android" se resuelve con un lanzador de módulos y no con compatibilidad con Android (Windows Subsystem for Android está discontinuado desde 2025), y el contrato permite cambiar de interfaz sin tocar el motor (FastAPI genera OpenAPI y soporta WebSockets, H22).
2. Etapa 0 (días, costo cero): núcleo Python sin interfaz (FastAPI en 127.0.0.1, base SQLite, sin recarga automática, versiones fijadas porque FastAPI y uvicorn siguen en 0.x), un lanzador de bandeja con pystray o, si ya usan Qt, QSystemTrayIcon, y arranque con el Programador de tareas al iniciar sesión. Por qué: un servicio de Windows no puede mostrar bandeja (H22) y esta combinación valida la idea sin aprender un framework nuevo. Evitar el modo normal de NiceGUI con host 0.0.0.0 (expone el servicio a la red local).
3. Etapa 1 (semanas): convertir el panel web existente en una PWA (manifiesto, service worker, HTTPS); en Windows instalarla desde Edge con inicio automático al iniciar sesión (H6); en Android acceder por una red privada con HTTPS (Tailscale Serve u opción equivalente, H23) y recibir las ofertas por ntfy (avisos desde el núcleo con un POST) o Web Push. No depender de Periodic Background Sync (experimental, Chromium, condicionado por interacción) ni de que el teléfono consulte precios cada pocos minutos (WorkManager exige 15 minutos y hay restricciones de segundo plano, H8). El rastreo debe quedar en Python por CORS (H7).
4. Distribución en Windows: preferir Microsoft Store con paquete MSIX (cuenta individual gratuita para uso no comercial, o cuenta de empresa también gratuita si es actividad comercial; la Store firma el MSIX), porque Azure Artifact Signing no está disponible para individuos en Argentina (H5). Si se distribuye un EXE fuera de la Store, asumir la advertencia de SmartScreen o evaluar un certificado comercial (no investigado aquí). Empaquetar el núcleo con PyInstaller o Briefcase (carpeta de app por defecto en Windows).
5. Android sin Google Play: si la PWA no alcanza, generar un APK con Bubblewrap (TWA) y distribuirlo con una cuenta de "distribución limitada" de la Android Developer Console (hasta 20 dispositivos, sin documento ni tarifa) o con el registro completo; la verificación empieza el 30/09/2026 en cuatro países y es global desde 2027 (H9). Revisar la política antes de cada versión y no asumir que el flujo avanzado de "apps no verificadas" seguirá igual.
6. Etapa 2 (meses): decidir el cliente nativo solo si aparecen límites reales de la PWA (bandeja avanzada, widgets, ejecución en segundo plano). Si Windows es lo principal: cliente en .NET 10 (Windows Forms o WPF con WebView2 y NotifyIcon), apoyado en LTS hasta 14/11/2028 (H2, H4). Si se quiere una sola base para ambas plataformas: Avalonia 12 (MIT, TrayIcon nativo, Android reescrito en la v12 según su proveedor) o Compose Multiplatform si se acepta Kotlin; en ambos casos el núcleo Python se mantiene como servicio y la app solo consume la API. Por qué: reescribir el motor en otro lenguaje no aporta nada y el 80% del valor está en el motor.
7. Qué evitar (y por qué): WinUI 3 si se necesita bandeja desde el primer día (sin API oficial, H4); .NET MAUI como apuesta a 5 años (soporte de MAUI 10 hasta 11/05/2027 y migración anual, H10); Electron y React Native si se quiere poco mantenimiento (migraciones cada ~6 meses y Electron sin Android, H15 y H16); Kivy (sin versión desde diciembre de 2024, H20); Flet como único cimiento (1.0 con tres semanas, bandeja sin confirmar, H21); Wails v3 y Tauri 3 hasta que salgan de beta/alfa (H14, H17).
8. Calendario de mantenimiento a 5 años: fijar fechas en un calendario propio: noviembre de 2026 (.NET 11 GA; .NET 8 y .NET 9 sin soporte el 10/11/2026), mayo de 2027 (fin de MAUI 10 y de servicio de Windows App SDK 2.0 el 29/04/2027 según la documentación), noviembre de 2028 (fin de .NET 10 LTS). Python 3.15 sale el 09/10/2026: PySide6 6.11.2 declara <3.15, así que conviene fijar Python 3.14 para el núcleo hasta que las dependencias lo soporten (H18).
9. Reducir la incertidumbre de tamaños con una prueba de un día: medir un "hola mundo" empaquetado de Tauri 2, Avalonia 12 y Flutter en Windows antes de elegir, porque esta investigación solo verificó dos cifras (Electron ~158 MB el entorno y PySide6 ~77 MB la rueda comprimida) y los blogs sobre tamaños se contradicen (H15).
10. Sol y Luna (rutinas de arranque y cierre) deben apoyarse en el Programador de tareas (disparadores al iniciar sesión, al arrancar, por hora, inactividad) y no en el planificador interno del núcleo; hay que verificar en el otro frente de la investigación las opciones de despertar el equipo y apagado, porque aquí solo se confirmó la lista de disparadores (H22).
11. Revisión fijada para noviembre de 2026: comprobar la salida de .NET 11, el estado de Tauri 3 y de Wails v3, la madurez de Flet 1.0 después de sus primeras actualizaciones y si Windows App SDK 2.x incorporó una API de bandeja, porque cualquiera de esos cambios altera el orden de preferencia anterior.

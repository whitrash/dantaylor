# Arquitectura de integración de módulos caseros para WINT (Osi, Sol, Luna, Detector, Catálogos y teléfono)

## Resumen

- Estado a 7 de octubre de 2026. Fuentes primarias abiertas: repositorios de GitHub (README, feeds Atom, API de releases), PyPI y la especificación MCP publicada en GitHub. Muchos sitios oficiales (tailscale.com, home-assistant.io, nodered.org, learn.microsoft.com, docs.python.org, sqlite.org, code.visualstudio.com) estaban bloqueados para WebFetch; en esos casos usé el código fuente o los .md/.rst equivalentes en GitHub, o resultados de búsqueda, y lo marco en la confianza.
- Patrón dominante en todos los ecosistemas personales estudiados (Home Assistant, Node-RED, VS Code, Obsidian, Flow Launcher, PowerToys Command Palette): un manifiesto declarativo por módulo + un registro central + un contrato de comunicación estrecho. Lo que cambia es el aislamiento: Obsidian carga plugins en el mismo proceso sin permisos reales; VS Code, Flow Launcher y Command Palette usan procesos aparte.
- Para un desarrollador solitario con núcleo Python/SQLite en Windows, el costo de mantenimiento más bajo es: módulos como procesos independientes, manifiesto JSON por módulo, API HTTP local (FastAPI) con SSE para eventos, y una tabla SQLite como bus de eventos. MQTT, NATS y Redis solo se justifican si hay Home Assistant/IoT de por medio; gRPC y named pipes no aportan ventaja real a esta escala.
- MCP es viable como interfaz OPCIONAL: la especificación estable vigente es 2026-07-28 (sin sesiones, sin handshake `initialize`, capacidades por solicitud); el SDK de Python `mcp` está en 2.3.0 (2 oct 2026). Un adaptador MCP delgado puede exponer los módulos como herramientas sin que WINT razone nada. Home Assistant ya hace exactamente eso (`/api/mcp`, solo entidades expuestas).
- Un ícono de bandeja (el del Detector) NO puede vivir dentro de un servicio de Windows (aislamiento de Session 0): el núcleo debe ser headless y la bandeja un cliente aparte. Esto condiciona toda la arquitectura.
- Planificador: APScheduler 3.11.3 (28 jun 2026) es la opción estable; la 4.x sigue en alfa con advertencia expresa de no usarla en producción. Su `misfire_grace_time` por defecto es 1 segundo: en una PC que suspende, los trabajos vencidos se pierden salvo que se configure.
- Servicios: Programador de tareas con disparador "al iniciar sesión" y reinicio ante falla cubre casi todo; si hace falta un servicio real, WinSW (estable 2.12.0, enero 2023) o NSSM (2.24, 2014) o pywin32 (build 312, 4 jun 2026). Celery no soporta Windows desde 4.x; Huey con SQLite sí encaja.
- Teléfono: Tailscale (cliente 1.102.5, 29 sep 2026) con `tailscale serve` (solo tailnet, HTTPS) es la opción de menor exposición; Funnel (internet pública) y ngrok/Cloudflare Tunnel son alternativas con más superficie. La vigencia exacta de los límites del plan gratuito de Tailscale NO pudo verificarse en la fuente oficial.
- Almacenamiento: Litestream (v0.5.17, 31 ago 2026) declara que Windows NO es plataforma soportada; en Windows conviene el API de respaldo en línea de `sqlite3` (`Connection.backup`). PocketBase, libSQL/Turso y Supabase sirven para una copia de lectura en la nube, cada uno con salvedades (pre-1.0, pausa por inactividad a los 7 días).
- Recomendación central: migrar de forma incremental (estado.json -> tabla `estado` + SSE; manifiesto por módulo; tabla `eventos`; planificador; tarea al iniciar sesión; Tailscale Serve; MCP al final), sin reescribir el motor `catalogo`.

## Hallazgos

### H1 — MCP: estado de la especificación a 2026
- Afirmación: La versión estable vigente de MCP es 2026-07-28 (publicada el 28 de julio de 2026); la anterior estable es 2025-11-25. El cambio central es un protocolo sin estado: desaparecen el handshake `initialize`/`initialized` y el encabezado `Mcp-Session-Id`; cada solicitud lleva su versión de protocolo, identidad de cliente y capacidades (en `_meta`). `server/discover` pasa a ser un RPC opcional. Las solicitudes HTTP llevan los encabezados `Mcp-Method` y `Mcp-Name` para enrutar sin leer el cuerpo. Las listas de herramientas/prompts/recursos incluyen `ttlMs` y `cacheScope`. "Tasks" pasa de experimental a la extensión formal `io.modelcontextprotocol/tasks` (consulta por sondeo con `tasks/get` y `tasks/update`), útil para trabajos largos como un barrido del Detector. Roots, Sampling y Logging pasan a obsoletos con una ventana mínima de soporte de 12 meses. Autorización: validación de emisor RFC 9207 y migración de Dynamic Client Registration hacia Client ID Metadata Documents. Hay coexistencia de eras: los clientes modernos sondean `server/discover` y, si falla, vuelven al `initialize` de la era anterior. Contradicción entre fuentes: el blog dice que el candidato a versión (RC) salió el 21 de mayo de 2026; la página de releases de GitHub lo fecha el 29 de mayo de 2026.

### H2 — MCP: transportes stdio y Streamable HTTP, y exigencias de seguridad
- Afirmación: En stdio el cliente lanza el servidor como subproceso; los mensajes JSON-RPC se delimitan con saltos de línea y NO pueden contener saltos de línea incrustados; el servidor puede escribir logs UTF-8 en stderr (el cliente puede capturarlos o ignorarlos y no debe tratarlos como error); el servidor debería salir pronto cuando se cierra su stdin. Consecuencia práctica: en un módulo que hable stdio, stdout queda reservado para el protocolo y no se puede usar `print()` de depuración. En Streamable HTTP el servidor expone un único endpoint MCP que acepta POST; los encabezados `MCP-Protocol-Version`, `Mcp-Method` y `Mcp-Name` son obligatorios según el caso, y el cliente debe enviar `Accept` con `application/json` y `text/event-stream`. Seguridad: el servidor DEBE validar el encabezado `Origin` (contra ataques de DNS rebinding), DEBERÍA enlazar solo a 127.0.0.1 y no a 0.0.0.0, y DEBERÍA autenticar todas las conexiones. La misma exigencia de `Origin`/localhost figura ya en 2025-11-25. Es una buena regla también para el panel actual en 127.0.0.1:8765 (opinión: cualquier página web abierta en el navegador puede intentar llamar a un servicio en loopback).
- Fuentes: https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/transports/stdio.mdx, https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx, https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2025-11-25/basic/transports.mdx
- Confianza: alta

### H4 — Precedente de MCP "opcional y determinista": Home Assistant lo expone sin razonar

### H5 — Home Assistant: núcleo (bus, máquina de estados, registro de servicios), entidades y automatizaciones
- Afirmación: El núcleo de Home Assistant se compone de cuatro piezas: Event Bus ("el corazón" que dispara y escucha eventos), State Machine (guarda estados y dispara `state_changed`), Service Registry (escucha eventos `call_service` y permite registrar acciones) y Timer (emite `time_changed` cada 1 segundo). Las entidades se identifican por dominio, plataforma e ID único (`unique_id`); el registro de entidades asegura que la misma entidad conserve siempre el mismo `entity_id`. Las automatizaciones se definen como disparador + condición (opcional) + acción, que es exactamente un modelo de reglas explícitas, sin conversación. La API WebSocket (`/api/websocket`) sigue el flujo `auth_required` -> `auth` con token -> `auth_ok`/`auth_invalid`, y luego comandos con `id` entero (`subscribe_events`, `call_service`, `get_states`). Lección: un bus de eventos + un registro de estado + un registro de servicios es suficiente para un ecosistema doméstico; WINT puede replicarlo con una tabla `estado`, una tabla `eventos` y un registro de módulos.
- Fuentes: https://raw.githubusercontent.com/home-assistant/developers.home-assistant/master/docs/architecture/core.md, https://raw.githubusercontent.com/home-assistant/developers.home-assistant/master/docs/api/websocket.md, https://raw.githubusercontent.com/home-assistant/home-assistant.io/current/source/_docs/automation/basics.markdown, https://developers.home-assistant.io/docs/entity_registry_index
- Confianza: alta
- Riesgo: bajo
- Vigencia: consultado 7 de octubre de 2026

### H6 — Home Assistant: el manifiesto de integración como modelo de manifiesto por módulo

### H10 — Obsidian: plugins en el mismo proceso, sin permisos reales
- Afirmación: Un plugin de Obsidian requiere `manifest.json` con `id`, `name`, `version` (SemVer), `minAppVersion`, `description`, `author` e `isDesktopOnly` (opcionales `authorUrl`, `fundingUrl`), y se distribuye como `main.js` + `manifest.json` + `styles.css` en una release de GitHub (con `versions.json` para compatibilidad). La documentación oficial afirma: "Obsidian cannot reliably restrict plugins to specific permissions or access levels" (los plugins heredan acceso a archivos, internet e instalación de programas); por defecto la app arranca en "Restricted Mode", que impide ejecutar código de terceros hasta que el usuario lo habilite; los plugins de la comunidad se escanean automáticamente en busca de vulnerabilidades y malware y se revisan manualmente los populares o marcados. La versión de escritorio más reciente en el repositorio de releases es 1.14.4 (5 de octubre de 2026). Lección: un manifiesto con "permisos" no es una frontera de seguridad si el código corre en el mismo proceso; para WINT conviene ejecutar cada módulo como proceso aparte y tratar los permisos del manifiesto como contrato y no como protección.

### H12 — Opciones de comunicación entre procesos en Windows y su costo de mantenimiento
- Afirmación: (a) Named pipes: Python los expone en `multiprocessing.connection` con direcciones de tipo `AF_PIPE` (`r'\\.\pipe\NombreDelPipe'`; para otra máquina `r'\\Servidor\pipe\Nombre'`); la autenticación usa una clave compartida por HMAC, y la documentación advierte que deserializar (pickle) datos de una fuente no confiable es un riesgo de seguridad. pywin32 incluye un ejemplo de servicio con tubería (`pipeTestService.py`: `win32serviceutil.ServiceFramework`, `CreateNamedPipe("\\\\.\\pipe\\PyPipeTest", PIPE_ACCESS_DUPLEX | FILE_FLAG_OVERLAPPED, ...)`). Solo funciona en Windows y exige E/S superpuesta si se quiere asíncrono. (b) stdio con JSON-RPC (como MCP y Flow Launcher): padre-hijo, sin red, muere con el padre; costo bajo. (c) HTTP local (FastAPI/Flask): reutilizable por navegador, teléfono y adaptador MCP; costo bajo, pero exige token y validación de `Origin`. (d) gRPC: `grpcio` 1.84.0 (14 sep 2026), Python 3.10+, ruedas para Windows x86-32/x86-64; exige definir esquemas protobuf y generar código; es la opción de mayor costo para un solitario. (e) Cola/bus: ver H13 y H14. Opinión: para un solo desarrollador, HTTP loopback (con JSON) para módulos persistentes y subproceso con salida JSON para trabajos por lotes cubren el 95% de los casos; named pipes y gRPC no ofrecen ventaja que justifique su mantenimiento. JSON-RPC 2.0 es el formato que ya comparten MCP y Flow Launcher, así que adoptarlo como contrato interno abarata el adaptador MCP posterior (su especificación no se pudo abrir: jsonrpc.org estaba bloqueado).
- Fuentes: https://raw.githubusercontent.com/python/cpython/main/Doc/library/multiprocessing.rst, https://raw.githubusercontent.com/mhammond/pywin32/main/win32/Demos/service/pipeTestService.py, https://pypi.org/project/grpcio/, https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/transports/stdio.mdx
- Confianza: media
- Riesgo: bajo
- Vigencia: consultado 7 de octubre de 2026

### H13 — Colas sobre SQLite y por qué Celery no encaja en Windows
- Afirmación: Huey 3.4.0 (4 de septiembre de 2026) soporta almacenamientos Redis, PostgreSQL, SQLite, sistema de archivos y memoria, ejecución multiproceso/multihilo/greenlet, tareas programadas y periódicas tipo cron, reintentos y prioridades. Su `SqliteHuey` usa solo el módulo estándar `sqlite3`, soporta prioridades, es configurable por `filename` (por defecto `huey.db`), `cache_mb` y `fsync`, y la documentación lo recomienda para desarrollo y despliegues en una sola máquina. LiteQueue 0.14 (31 de julio de 2026) es una cola persistente sobre SQLite (`put()`, `pop()`, `done()`, sin dependencias, Python 3.12+); persist-queue 1.1.0 (25 de octubre de 2025) ofrece colas en SQLite con confirmación (ack), con soporte para Windows. Celery (5.6.3, 26 de marzo de 2026) requiere un broker (RabbitMQ o Redis, entre otros) y su FAQ dice textualmente que "desde Celery 4.x, Windows ya no está soportado por falta de recursos" (puede funcionar pero no hay garantía). ### H16 — Programador de tareas de Windows (y systemd timers para el caso Linux/WSL)

### H17 — Aislamiento de Session 0: un servicio de Windows no puede mostrar la bandeja

### H19 — Registros (logs) y rotación con varios procesos en Windows
- Afirmación: La documentación del módulo `logging` de Python establece que registrar en un único archivo desde varios procesos "no está soportado, porque no hay una forma estándar de serializar el acceso a un archivo entre procesos"; las alternativas documentadas son: (1) `SocketHandler` con un proceso receptor que escribe el archivo, (2) `QueueHandler` en cada proceso y un `QueueListener` en un proceso aparte que escribe el archivo, o (3) un manejador propio con `multiprocessing.Lock`. Opinión de diseño: cada módulo escribe su propio archivo rotado (`RotatingFileHandler`) o todos envían a una tabla SQLite `logs`; el núcleo no comparte un mismo archivo entre procesos.

- Afirmación: ntfy es un servicio de notificaciones pub/sub por HTTP (se publica con PUT/POST a un "topic" y se recibe en el teléfono); sin registro obligatorio, con apps para Android (Google Play y F-Droid) y iOS, autoalojable, con licencia dual Apache-2.0 y GPLv2; la instancia pública gratuita es ntfy.sh y hay un plan hospedado ntfy Pro desde 5 USD al mes. ## Recomendaciones para WINT

1. Separar un núcleo headless de los clientes de interfaz. Porque el aislamiento de Session 0 impide que un servicio muestre el ícono de bandeja (H17): el núcleo (FastAPI + planificador + almacén) corre sin ventana, y la bandeja del Detector, el panel web y el teléfono son clientes que lo consultan por HTTP/SSE.
2. Definir un manifiesto por módulo (`modulo.json` o `modulo.toml`) y un registro que lo lee desde una carpeta `modulos/`. Campos sugeridos, tomados de Home Assistant, VS Code y Obsidian (H6, H9, H10): `id`, `nombre`, `version`, `tipo_interfaz` (`cli`, `http` o `stdio`), `comando`, `puerto` (si es http), `eventos_que_emite`, `eventos_que_escucha`, `programacion_por_defecto`, `activacion` (al iniciar sesión, por horario, por evento), `permisos_declarados` (red, archivos, notificaciones), `dependencias` y `salud` (ruta de chequeo). Porque el núcleo así sabe qué esperar sin ejecutar nada, y el mismo manifiesto alimenta la tabla de herramientas del adaptador MCP.
3. Ejecutar cada módulo (Osi, Sol, Luna, Detector, Catálogos) como proceso independiente; no importar módulos dentro del núcleo. Porque Obsidian muestra que un manifiesto de permisos sin aislamiento real no protege (H10) y VS Code/Flow Launcher/Command Palette aíslan por proceso (H9, H11); además un módulo que falla no tumba a los demás.
4. Adoptar un solo contrato interno: JSON sobre HTTP local para módulos persistentes y subproceso con salida JSON (`stdout`) para trabajos por lotes, con mensajes con forma JSON-RPC 2.0. Porque es lo que ya usan MCP y Flow Launcher (H2, H11, H12), evita named pipes y gRPC (costo alto, ventaja nula a esta escala) y deja el adaptador MCP casi gratis. Regla práctica heredada de stdio: ningún `print()` de depuración en `stdout` de módulos que hablen JSON.
5. Implementar el bus de eventos como una tabla SQLite `eventos` (id autoincremental, marca de tiempo, origen, tipo, JSON, id de correlación) con una tabla `cursores` (consumidor, último id leído) y notificar a los clientes por SSE (FastAPI 0.135+). Porque replica el núcleo de Home Assistant (bus + estado + servicios, H5) sin broker extra (H13, H14). Pasar a Mosquitto solo si se integra Home Assistant u otros dispositivos que ya hablan MQTT.
6. Usar APScheduler 3.11.x (no 4.x) con almacén persistente, `id` explícito y `replace_existing=True`, y fijar `misfire_grace_time` alto y `coalesce=True` en Sol y Luna. Porque el valor por defecto es 1 segundo (H15) y una PC que suspende perdería las rutinas; verificá el comportamiento con una prueba real de suspensión antes de confiar en él.
7. Lanzar el núcleo con el Programador de tareas ("al iniciar sesión", `schtasks /create ... /sc onlogon`, `RestartOnFailure` con `Count` e `Interval` de al menos 1 minuto, `MultipleInstancesPolicy=IgnoreNew`) en lugar de un servicio. Porque el núcleo y la bandeja comparten sesión de usuario y no hace falta WinSW/NSSM/pywin32 (H16, H17, H18); recién si necesitás que corra antes de iniciar sesión, usá WinSW 2.12.0 con `<onfailure action="restart" delay="10 sec"/>` y un cliente de bandeja separado.
8. Registros: un archivo rotado (`RotatingFileHandler`) por módulo, o un único proceso de log con `QueueHandler`/`QueueListener`; nunca varios procesos escribiendo el mismo archivo y nada de `WatchedFileHandler` en Windows (H19).
9. Migrar `estado.json` por etapas: (a) escribirlo con archivo temporal + `os.replace()`; (b) agregar el endpoint `/estado` y la tabla `estado`; (c) servirlo por SSE a la bandeja y al panel; (d) apagar el espejo cuando nadie lo lea (H20). Porque elimina lecturas parciales y las 86.400 escrituras diarias.
10. Seguridad local mínima: enlazar solo a 127.0.0.1, exigir un token en cada llamada, validar `Origin` y rechazar con 403 los orígenes desconocidos (la especificación MCP lo exige para sus servidores locales, H2). Porque el panel en 127.0.0.1:8765 hoy queda a merced de cualquier página abierta en el navegador (opinión razonada).
11. Teléfono: instalar Tailscale en la PC y el teléfono y publicar el panel con `tailscale serve --bg 8765` (solo tailnet, HTTPS con certificado de la tailnet); no usar Funnel. Alternativas si no querés VPN: Cloudflare Tunnel + Access (necesita dominio en Cloudflare) o ngrok solo para demos (límites del plan gratis en H22). Verificá en la página oficial de Tailscale los límites vigentes del plan Personal antes de depender de ellos (H21).
12. Avisos: un notificador determinista que haga POST a un topic de ntfy (autoalojado o ntfy.sh con nombre de topic largo y aleatorio) más una notificación de Windows en la PC. Porque cubre "te aviso de la oferta" sin que WINT converse ni pregunte (H25).
13. Respaldos y copia de lectura: en Windows usar `sqlite3.Connection.backup()` (no Litestream, que no es oficial allí, H23) programado por Luna, y subir la copia a un destino de tu elección. Solo si querés ver ofertas con la PC apagada, publicar un resumen de solo lectura en PocketBase o Supabase (límites y pausa por inactividad en H24); la PC sigue siendo la fuente de verdad.
14. MCP al final y como adaptador separado (`wint-mcp`), por stdio para uso local y Streamable HTTP detrás de Tailscale para uso remoto: exponer una lista blanca de 5 a 10 herramientas (listar productos, consultar ofertas, ejecutar Sol/Luna, estado de módulos), la mayoría de solo lectura, construida sobre la API HTTP y el manifiesto. Porque la especificación 2026-07-28 es estable, el SDK `mcp` 2.x ya la soporta (H1, H3), y Home Assistant demuestra el patrón de "solo entidades expuestas" (H4). Evitar Sampling (obsoleto) para que WINT no dependa de ningún modelo; usar la extensión Tasks para barridos largos.
15. Interpretar la analogía "plataforma Android" como tres piezas concretas: un lanzador/registro de módulos (el manifiesto), un sistema de intents (los eventos de la tabla `eventos` con nombres estables como `precio.oferta_detectada`) y un contrato de permisos declarados que el núcleo valida por convención, sabiendo que no es una frontera de seguridad (H10). Es una analogía de diseño propia; no se verificó documentación de Android.
16. Orden de migración incremental recomendado (ver el diagrama de la siguiente sección): fase 0 congelar contratos y estado; fase 1 manifiesto + registro de módulos que envuelvan el motor `catalogo` sin cambiarlo; fase 2 tabla `estado` + SSE; fase 3 tabla `eventos`; fase 4 planificador y Sol/Luna como módulos; fase 5 tarea al iniciar sesión + bandeja cliente; fase 6 Tailscale Serve y ntfy; fase 7 adaptador MCP.

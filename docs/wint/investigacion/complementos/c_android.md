## Q1. Android developer verification: cronograma, sideloading, adb, flujo avanzado, cuentas

### Respuesta concreta
1. Cronograma oficial (vigente a 7 de octubre de 2026): junio de 2026, despliegue del servicio del sistema y acceso anticipado a cuentas de distribución limitada; julio, API de estado global y acceso anticipado a la API de Consola; agosto de 2026, lanzamiento global de la API de Consola, de las cuentas de distribución limitada y del flujo avanzado; 30 de septiembre de 2026, aplicación efectiva en Brasil, Indonesia, Singapur y Tailandia; "2027 y más adelante", ampliación global. Hoy (7 de octubre) el 30 de septiembre ya pasó y la fase de cuatro países está en curso. No encontré ningún anuncio posterior que cambie el calendario.
2. Alcance del 30 de septiembre de 2026: solo las siete tiendas participantes (Google Play, HONOR App Market, OPPO App Market, Samsung Galaxy Store, Transsion Palm Store, vivo V-Appstore, Xiaomi GetApps), solo dispositivos certificados con Android 7 o superior, y solo formatos móvil y tableta.
3. ## Q2. Android 17 y target API de Google Play

### Respuesta concreta
1. Android 17: versión estable lanzada el 16 de junio de 2026 (primero en Pixel 6 en adelante); nivel de API 37 (SDK_INT = 37). Existe además una versión menor de plataforma en el ciclo (QPR1, API 37.1; QPR2 en beta con API 37.2, según la página de versión).
2. Target API de Google Play vigente en 2026: desde el 31 de agosto de 2026, las apps nuevas y las actualizaciones deben apuntar a Android 16 (API 36) o superior (Wear OS y Android Automotive OS: API 35; Android TV y Android XR: API 34). Las apps existentes deben apuntar a API 35 o superior para seguir visibles a usuarios nuevos en dispositivos con Android más nuevo que su target. Se puede pedir una prórroga hasta el 1 de noviembre de 2026; los formularios llegarán a Play Console "later this year" (todavía no confirmado que estén disponibles). Exentas: apps privadas permanentes de una organización.
3. 2027: NO hay una exigencia de API 37 publicada oficialmente. La página oficial de Android (actualizada el 1 de octubre de 2026) no menciona API 37 ni 2027. La regla general de Play, según un extracto de búsqueda de su página de política, es apuntar a un nivel "within one year of the latest major Android release"; con Android 17 lanzado el 16 de junio de 2026, lo esperable (inferencia, no anuncio) es que Play exija API 37 hacia el 31 de agosto de 2027, siguiendo el patrón API 35 (2025) y API 36 (2026). Dos sitios secundarios lo afirman como hecho, sin fuente oficial.

2. Estado hoy (octubre de 2026): discontinuado, sin actualizaciones ni correcciones de seguridad. Un resultado de búsqueda de Microsoft Q&A indica que el paquete aún puede instalarse pero los componentes de ejecución necesarios para abrir apps fueron deshabilitados (indicio de confianza media-baja; no abrí esa página).

Lo que existe son alternativas de terceros (emuladores como BlueStacks, MuMu, LDPlayer), Google Play Games para PC (solo juegos, producto de Google, no un runtime general de Android) y Phone Link (que refleja o controla el teléfono, no ejecuta apps en la PC). Para WINT: sigue descartado como herramienta de prueba; para desarrollo, emulador de Android Studio con WHPX o un teléfono físico.

## Q5. WorkManager y alarmas exactas

### Respuesta concreta
1. WorkManager: el intervalo mínimo de trabajo periódico es de 15 minutos (igual que JobScheduler). Versión estable actual: 2.12.0 (23 de septiembre de 2026; minSdk 24).
2. Alarmas exactas, documentación de Android: la mayoría de las apps debe usar alarmas inexactas; las exactas están pensadas para apps cuya función central depende de una hora precisa, como un despertador o un calendario. SCHEDULE_EXACT_ALARM lo concede el usuario, es revocable, cubre más casos de uso y no viene preconcedido en instalaciones nuevas con target 13 o superior. USE_EXACT_ALARM se concede automáticamente y no es revocable, tiene casos de uso limitados y está sujeto a la política de Google Play.
3. Política de Play (extracto de búsqueda, sin abrir la página): USE_EXACT_ALARM es un permiso de acceso restringido; solo se puede declarar si la función central de la app es una alarma o temporizador, o un calendario que muestra notificaciones de eventos. Hay que completar una declaración en Play Console y las apps que piden el permiso sin cumplir el uso aceptable pueden ser rechazadas. Para el resto, la alternativa es SCHEDULE_EXACT_ALARM (con consentimiento del usuario). La documentación de Android todavía llama "upcoming" a esta política de Play; no pude determinar su fecha de entrada en vigor.
4. Consecuencia para WINT (Sol y Luna son rutinas a una hora fijada, no un reloj ni un calendario de eventos): no corresponde pedir USE_EXACT_ALARM para publicar en Play; usar WorkManager (con tolerancia de ventana), alarmas inexactas, o SCHEDULE_EXACT_ALARM con pantalla de consentimiento si hace falta precisión. Si WINT se instala por APK directo, la política de Play no aplica, pero los límites de Android sí.

### Evidencia
- WorkManager (https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work, "Last updated 2026-10-01 UTC", vía WebFetch): "Note: The minimum repeat interval that can be defined is 15 minutes (same as the JobScheduler API)." Y: "The repeat interval must be greater than or equal to PeriodicWorkRequest.MIN_PERIODIC_INTERVAL_MILLIS and the flex interval must be greater than or equal to PeriodicWorkRequest.MIN_PERIODIC_FLEX_MILLIS."
- Versión (https://developer.android.com/jetpack/androidx/releases/work, vía WebFetch): "Stable Release 2.12.0 September 23, 2026"; "Updated minSdk from API 23 to API 24".

## Cambios que esto impone al informe

1.

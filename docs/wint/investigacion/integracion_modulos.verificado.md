## Correcciones clave (lo que cambia el informe)

1. MCP, `server/discover` (H1): el investigador lo describe como "RPC opcional". Es al revés para el servidor: la especificación 2026-07-28 dice que los servidores DEBEN implementar `server/discover` (MUST) y que los clientes PUEDEN llamarlo antes de otras solicitudes (MAY). Lo opcional es que el cliente lo use, no que el servidor lo exponga. Un adaptador `wint-mcp` hecho con el SDK `mcp` 2.x lo trae resuelto, pero si se escribiera a mano hay que implementarlo.
2. MCP, fechas del candidato a versión (H1 y tabla): no hay contradicción. El blog dice que el RC quedó "bloqueado" (locked) el 21 de mayo de 2026 y que la especificación final saldría el 28 de julio de 2026; la página de releases de GitHub fecha la pre-publicación del RC el 29 de mayo de 2026 (12:51) y la estable el 28 de julio de 2026 (16:47). Texto sugerido: "RC fijado el 21 may 2026; pre-release en GitHub el 29 may 2026; estable 2026-07-28".
3. Flow Launcher no usa JSON-RPC 2.0 ni stdin/stdout (H11, H12, recomendación 4, fila "JSON-RPC 2.0"): el paquete oficial `flowlauncher` 0.2.0 recibe la solicitud como JSON en el primer argumento de línea de comandos (`sys.argv[1]`, con forma `{"method": "query", "parameters": [...]}`, sin campo `jsonrpc` ni `id`) y responde imprimiendo un JSON propio (`{"result": ..., "debugMessage": ...}`) por stdout. Por lo tanto, "JSON-RPC 2.0 es el formato que ya comparten MCP y Flow Launcher" es falso: solo MCP usa JSON-RPC 2.0 estricto. Flow Launcher sirve como precedente de "proceso hijo + JSON", no de JSON-RPC 2.0. La recomendación 4 sigue siendo válida si se adopta JSON-RPC 2.0 por decisión propia (por afinidad con MCP), pero hay que quitar a Flow Launcher como argumento.
4. Huey en Windows (H13, fila Huey): la documentación del consumidor de Huey advierte que "el soporte multiproceso no está disponible en Windows" (solo existe el método de arranque "spawn" y el estado de Huey no se puede serializar con pickle). En Windows hay que usar el tipo de worker `thread` (el valor por defecto) o `greenlet`; `-k process` no sirve. Licencia: MIT. Además Huey tiene `PostgresHuey` (no solo Redis/SQLite/archivo/memoria).
5. ntfy en Windows (H25, fila ntfy): la nota "soporte oficial no confirmado" queda resuelta. La documentación de instalación de ntfy dice textualmente que "el servidor y la CLI de ntfy están totalmente soportados en Windows", ofrece un ZIP `ntfy_2.28.0_windows_amd64.zip`, instalación con Scoop y ejemplo de servicio con `sc create ntfy binPath="C:\ruta\ntfy.exe serve" start=auto`; el archivo de configuración por defecto es `%ProgramData%\ntfy\server.yml`.
6. Home Assistant, tipos de instalación (H7, fila Home Assistant): la página oficial de instalación (rama `current`) ya solo presenta dos tipos: Home Assistant OS (con Apps) y Home Assistant Container (sin Apps, "no tienen acceso a Apps"). No menciona "Supervised" ni "Core". Texto corregido: "las Apps solo existen en Home Assistant OS; la instalación Container no las tiene". El cambio de nombre add-ons a apps queda confirmado por las notas de la versión 2026.2 (4 de febrero de 2026). El nombre "App Store" no figura en esas notas (no verificado). Licencia de Home Assistant Core: Apache-2.0.
7. Programador de tareas, reinicio ante falla (H16, recomendación 7): el esquema XML define `RestartOnFailure/Count` como `unsignedByte` con mínimo 1; la cifra "máximo 999" NO figura en la documentación del esquema y un byte sin signo no puede pasar de 255. `Interval`: mínimo 1 minuto y máximo 31 días (confirmado). Además `schtasks /create` no tiene parámetros para reinicio ante falla: eso se configura con XML (`/xml`) o con PowerShell (`New-ScheduledTaskSettingsSet -RestartCount -RestartInterval`), y la documentación de `schtasks` indica que solo los administradores pueden programar tareas. La recomendación 7 debe decir "ejecutar `schtasks /create` desde una consola elevada o importar un XML con `RestartOnFailure`".
8. Node-RED en Windows (H8): la documentación oficial de Windows sugiere el Programador de tareas con disparador "Al iniciar el sistema" (acción `node-red.cmd`) y PM2; NSSM no figura en esa página. Corregir "Programador de tareas o PM2/NSSM" por "Programador de tareas (al iniciar el sistema) o PM2". El resto (5.0.0 el 9 jun 2026, exige Node.js 22.9 o superior, 5.0.7 el 8 sep, 4.1.15 el 9 sep) está confirmado con el registro de npm.
9. Reemplazo atómico de `estado.json` en Windows (H20, recomendación 9): lo documentado es que `os.replace()` es atómico "requisito POSIX" y reemplaza en silencio si hay permiso. NO pude verificar con fuente abierta qué pasa en Windows cuando otro proceso (la bandeja, el panel) tiene el destino abierto: es un riesgo conocido de Windows que `os.replace` falle con `PermissionError` si el lector no abrió el archivo con permiso de borrado/renombrado compartido. Recomendación defensiva (no verificada aquí): el escritor debe reintentar ante `PermissionError` unas pocas veces con una pausa breve, y el lector debe tolerar un JSON ausente o inválido.
10. Tailscale (H21): sigue sin poder verificarse con fuente oficial que el plan Personal sea gratis hasta 3 usuarios y 100 dispositivos, ni si Funnel está incluido en el plan gratuito. Lo técnico sí está confirmado en el código fuente: `tailscale serve --bg 3000` figura literalmente en la ayuda del CLI, y los puertos de Funnel los define el atributo de nodo `CapabilityFunnelPorts` que impone el servidor de control. Como la recomendación es no usar Funnel, el riesgo para el informe es bajo; hay que dejar la frase "verificá los límites vigentes en tailscale.com" tal cual.

12. Litestream (H23): confirmado que Windows "NO es una plataforma oficialmente soportada" (nota de la v0.5.17), versión 0.5.17 del 31 de agosto, estado beta y tabla `_litestream_lock`. Pero el README abierto solo dice que replica "a otro archivo o a S3"; la lista "S3, GCS, Azure, SFTP", "un solo escritor" y "un único destino de réplica" no figura en ese README (no verificado aquí).
13. WinSW (H18): las fechas están confirmadas (2.12.0 el 28 de enero de 2023; 3.0.0-alpha.11 el 29 de enero de 2023; la rama de la 2.12.0 muestra como último commit el 19 de enero de 2023). Matiz: el investigador cita la documentación de la rama v3; en la 2.12.0 la sintaxis de inicio retrasado es el elemento vacío `<delayedAutoStart/>` (en la v3 es `<delayedAutoStart>true</delayedAutoStart>`); `<onfailure>`, `<resetfailure>` y `<log mode="roll">` existen en ambas.

Datos que el investigador no pudo obtener y ahora están: zeroconf 0.151.5 (28 sep 2026, LGPL-2.1-or-later, Python 3.10 o superior); WireGuard para Windows, última etiqueta v1.1.1 (20 sep 2026, según el espejo de GitHub; la descarga oficial está bloqueada); pystray 0.19.5 (17 sep 2023, LGPLv3, sin versiones desde 2023, hay que considerarlo poco mantenido); ntfy server en Windows soportado (ver punto 5).

Sin errores graves de fondo: no hay ningún hallazgo REFUTADO. Las versiones y fechas de PyPI, npm y GitHub (mcp 2.3.0, FastAPI 0.142.2, uvicorn 0.54.0, grpcio 1.84.0, huey 3.4.0, APScheduler 3.11.3, pywin32 312, nats-py 2.16.0, Node-RED 5.0.7, Home Assistant 2026.9.4, Tailscale 1.102.5, VS Code 1.140.0, Obsidian 1.14.4, Litestream 0.5.17, Syncthing 2.1.6, ntfy 2.28.0, PocketBase 0.40.4, cloudflared 2026.10.0, Redis 8.10.2, NATS 2.15.0, Mosquitto 2.1.2) coinciden con lo que afirma el investigador.
